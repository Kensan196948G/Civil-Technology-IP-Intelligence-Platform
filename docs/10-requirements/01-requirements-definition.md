## 1. はじめに

### 1.1 本書の目的

本書は CTIIP が満たすべき要件を定義し、設計・実装・テストの基準を与える。
機能要件の網羅的な一覧は [02-functional-requirements.md](02-functional-requirements.md) に、
非機能要件は [03-non-functional-requirements.md](03-non-functional-requirements.md) に分離する。

### 1.2 適用範囲

CTIIP の全モジュール（M01〜M25）および外部連携。
`Construction-LegalOps-DX` 側の要件は本書の対象外とし、境界のインターフェースのみ定義する。

### 1.3 要件の優先度

| 記号 | 意味 | 判定 |
|---|---|---|
| **MUST** | 必須。これがなければリリースしない | 全フェーズの受入条件 |
| **SHOULD** | 重要。原則実装するが、理由を記録すれば延期可 | フェーズ末レビューで判断 |
| **COULD** | 望ましい。余力がある場合に実装 | 任意 |
| **WON'T** | 今回は実装しない | 対象外として明記 |

## 3. 業務要件

### 3.1 業務フロー（発明）

```text
①課題・発明の登録   （作業所／船舶／支店）
   ↓
②先行技術調査       （技術・研究開発、システムが支援）
   ↓
③AI模擬審査         （システム。人の検証必須）
   ↓
④社内レビュー       （技術＋安全品質環境＋管理本部）
   ↓
⑤決裁               （経営・委員会）
   ↓
──────────── 責任境界 ────────────
   ↓
⑥権利化・契約       （Construction-LegalOps-DX）
```

差戻し経路を④→①に必ず設ける。否となった案件は理由つきで起案者へ戻る。

### 3.2 業務フロー（現場技術の選定）

```text
①現場課題の登録 → ②適用可能技術の抽出 → ③現場適用性評価（スコア）
   → ④安全・品質・環境の導入可否判断 → ⑤試行または本格導入
```

**MUST**: ③のスコアが高いことは④の可否判断を代替しない。④を承認フロー上の必須ステップとする。

### 3.3 業務フロー（ライセンス導入）

```text
①技術ニーズの登録 → ②ライセンス候補の探索 → ③技術適合評価・Buy/Build/Partner比較
   → ④法務確認事項の整理 → ⑤決裁 → ⑥ LegalOps へ引き渡し
```

## 6. データ要件

### 6.1 データ分類

| 区分 | 例 | 取扱 |
|---|---|---|
| **C1 公開** | 公開特許、公開論文、NETIS、技術基準 | 社内自由閲覧 |
| **C2 社内** | 技術台帳、施工実績、過去調査、AIレビュー | 所属・プロジェクト単位で制御 |
| **C3 機密** | 出願前の発明情報、Claim候補、競合評価 | プロジェクト参加者のみ。エクスポート制限 |
| **C4 最高機密** | 未公開の重要発明、係争関連情報 | 個別付与。監査ログ強化 |

**MUST**: 全レコードに分類区分を持たせ、権限判定と AI 送信可否判定に用いる。

### 6.2 外部データ源

| 源 | 内容 | 取得方式 | 状態 |
|---|---|---|---|
| JPO / J-PlatPat 系 | 国内特許の書誌・請求項・審査経過 | ⚠️ **要決定** | 利用条件確認中 |
| WIPO | 国際出願・ファミリー | ⚠️ **要決定** | 利用条件確認中 |
| 公開論文・研究情報 | 論文書誌・要旨・引用 | ⚠️ **要決定** | 利用条件確認中 |
| NETIS・国交省公開情報 | 新技術情報、技術基準 | ⚠️ **要決定** | 利用条件確認中 |
| Construction-LegalOps-DX | 契約・権利状態 | 非同期メッセージ | Phase 4 |

**MUST**: 取り込んだ全レコードに `source`, `source_url`, `retrieved_at`, `license_note` を保持する。

### 6.3 データ品質

**MUST** — 出願人・発明者の名寄せ、企業名統一、特許ファミリー統合、重複除去、IPC/CPC 正規化、日付正規化、国コード統一、工種分類の付与。
名寄せは自動候補提示 + 人による確定の二段階とし、確定操作を監査ログに残す。

## 8. 制約条件

| # | 制約 | 影響 |
|---|---|---|
| C-01 | 実行基盤は Cloudflare Workers。1リクエストのCPU時間に上限がある | 長時間処理は Workflows / Queues へ分離する（[ADR-0004](../20-architecture/adr/ADR-0004-async-ai-execution.md)） |
| C-02 | Neon の PostgreSQL には日本語形態素解析拡張（PGroonga 等）が無い | 字句検索は pg_trgm、意味検索は pgvector のハイブリッドとする（[ADR-0003](../20-architecture/adr/ADR-0003-japanese-search.md)） |
| C-03 | 公開DNS・custom domain の変更は承認事項 | 手順書化し、実行前に 🔒 承認を得る |
| C-04 | 本番シークレットの投入・更新は承認事項 | 同上 |
| C-05 | 未公開発明を外部AIへ送信する範囲は要規程 | AI送信ポリシーを Phase 0 で整備 |
| C-06 | 外部データ源の再配布は原則不可 | エクスポート機能に出典表記と件数制限を設ける |

## 9. 前提条件

| # | 前提 | 未成立時の影響 |
|---|---|---|
| P-01 | 外部データ源の利用契約が締結できる | 検索対象が自社データのみに縮退し、価値が大きく減じる |
| P-02 | 職務発明規程・AI利用ポリシーが Phase 1 開始前に整備される | 発明管理モジュールを稼働できない |
| P-03 | Cloudflare / Neon のアカウントと権限が付与されている | 環境構築に着手できない |
| P-04 | `mirai-dx-platform.com` の DNS を Cloudflare で管理できる | サブドメイン発行手順の見直しが必要 |
| P-05 | 推進事務局に専任相当の要員を配置できる | Phase 2 以降が停滞する |
