# 🌿 ブランチ戦略と PR 運用

## 1. ブランチ

| ブランチ | 役割 | 保護 |
|---|---|---|
| `main` | 常にデプロイ可能な状態。mvp へ自動デプロイ | 保護あり。直接 push 禁止 |
| `feat/*` | 機能追加 | — |
| `fix/*` | 不具合修正 | — |
| `chore/*` | 雑務（依存更新、設定） | — |
| `docs/*` | ドキュメントのみ | — |
| `refactor/*` | 挙動を変えない整理 | — |

**命名**: `feat/FR-M06-002-claim-decompose` のように**要件IDを含める**。

## 2. main の保護設定

| 設定 | 値 |
|---|---|
| 直接 push | 禁止 |
| PR 必須 | 有効 |
| 必須チェック | lint / typecheck / test / build / security scan |
| レビュー | 1名以上の承認（⚠️ 人数は要決定） |
| 会話の解決 | 必須 |
| 最新化 | マージ前に main を取り込むこと |
| force push | 禁止 |
| 履歴改変 | 禁止 |

## 3. コミット

Conventional Commits に従う。

```text
feat(claim): 請求項の構成要件分解を追加

FR-M06-002 に対応。AI の出力を Zod で検証し、
ai_citations を必ず作成する。引用文は原文から切り出す。

Refs: FR-M06-002, ADR-0006
```

| 型 | 用途 |
|---|---|
| `feat` | 機能追加 |
| `fix` | 不具合修正 |
| `docs` | ドキュメント |
| `refactor` | 挙動を変えない整理 |
| `test` | テスト |
| `chore` | 雑務 |
| `perf` | 性能改善 |

**MUST**: コミット単位を論理的に保つ。無関係な変更を混ぜない。

## 4. PR テンプレート

```markdown
## 目的
（何のための変更か。対応する要件ID）

## 変更内容
- 

## 影響範囲
（モジュール、DB、API、画面。既存機能への影響）

## テスト結果
- [ ] lint / typecheck / test / build
- [ ] 権限テスト（拒否が効くこと）
- [ ] Provenance テスト（AI変更時）
- [ ] 手動確認（内容を記載）

## セキュリティ
- [ ] シークレットを含まない
- [ ] 権限条件が SQL に含まれている
- [ ] 機密区分の扱いが正しい

## マイグレーション
- [ ] なし
- [ ] あり（加算のみ・後方互換）／ロールバック手順：

## デプロイ
（特別な手順の有無）

## ロールバック方法
（切り戻し手順）

## 残課題
- 

Refs: FR-xxx, UC-xx, ADR-xxxx
```

## 5. レビュー観点

| 区分 | 観点 |
|---|---|
| 正しさ | 要件を満たしているか。境界条件の扱い |
| 権限 | 権限判定の抜けがないか。404 と 403 の使い分け |
| Provenance | AI変更なら `ai_citations` が作られるか |
| セキュリティ | シークレット、入力検証、SQLインジェクション、機密の露出 |
| 性能 | N+1、不要な全走査、同期での長時間処理 |
| 保守性 | 命名、責務分離、重複、テストの有無 |
| 文書 | 要件・設計・README の更新が必要か |

**重大度の扱い**

| 重大度 | 対応 |
|---|---|
| Critical / High | 修正なしにマージしない |
| Medium | 原則修正。理由を記録すればスキップ可 |
| Low | 任意 |

## 6. マージ

| 項目 | 方針 |
|---|---|
| 方式 | Squash merge |
| タイトル | Conventional Commits 形式 |
| 条件 | 必須チェック全通過 + レビュー承認 + 会話解決 |
| 禁止 | 保護規則の迂回、force push、CI未通過マージ |

## 7. リリース

```text
main が受入完了
   ↓
タグ作成  v0.1.0（セマンティックバージョニング）
   ↓
🔒 本番デプロイの承認（GitHub Environments の Required reviewers）
   ↓
本番デプロイ → スモークテスト
   ↓
リリースノート作成（変更・影響・ロールバック手順）
```

## 8. WorkTree の利用

複数の作業を並行させる場合は git worktree を使い、ブランチの切り替えによる作業消失を防ぐ。
1つの作業単位につき1つの worktree とする。
