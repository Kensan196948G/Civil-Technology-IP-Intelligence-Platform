# ADR-0005 認証を Cloudflare Access に委ね、アプリは認可のみ担う

| 項目 | 値 |
|---|---|
| 状態 | 採択 |
| 日付 | 2026-08-22 |

## 文脈

要件として SSO と MFA が MUST である（NFR-S-001）。
本システムは未公開の発明情報（C3/C4）を扱うため、認証の実装ミスは致命的である。
一方、開発チームの規模は限られており、認証基盤を自前で実装・保守する余力はない。

## 決定

- **認証（誰であるか）** は Cloudflare Access に委ねる。SSO・MFA・デバイス条件は Access のポリシーで設定する
- **認可（何ができるか）** はアプリケーションが担う。RBAC + プロジェクト単位の行レベル制御 + 機密区分
- アプリは `CF-Access-JWT-Assertion` を検証して利用者を特定する。ログイン画面もパスワードもアプリ側に持たない

## 理由

- MFA・SSO・セッション管理を自前実装するリスクを負わない
- 未認証のリクエストがアプリに到達しない（多層防御）
- IdP の変更（Entra ID / Google Workspace 等）がアプリ改修なしで可能
- 認証と認可を分離することで、認可のテストに集中できる

## 結果

**良い点**: 認証の実装責任を負わない。入口で遮断できる。IdP 変更に強い
**悪い点 / 注意点**:

- Cloudflare Access への依存が生じる
- ⚠️ **JWT 検証を必ず行う**。ヘッダの存在だけを信頼してはならない（Access を経由しない経路が万一あると認証を素通りする）
- API を Worker 間で直接呼ぶ経路には別途内部トークンが必要
- ローカル開発では Access を経由しないため、開発用の擬似利用者機構が必要（本番ビルドでは無効化する）

**必須の実装ルール**

1. JWT の署名・`aud`・`iss`・有効期限を毎回検証する
2. 検証をミドルウェアで一元化し、個別ハンドラに委ねない
3. 開発用の擬似認証は環境変数で分岐し、本番ビルドに含めない
4. Worker 間呼び出しは Service Binding + 内部トークンで保護する

## 代替案

| 案 | 不採用の理由 |
|---|---|
| アプリ内で認証を自前実装 | MFA・SSO の実装リスク。保守コスト |
| 外部の認証SaaSをアプリに組み込む | Cloudflare 一本化の方針から外れる。入口での遮断ができない |

## 再評価条件

- 社外の協力会社・大学等へ限定的にアクセスを開放する要件が発生した場合（Access のポリシー設計で対応可能か再検討）
- IdP 側の制約で Access と接続できない場合
