# ADR-0004 AI処理を非同期（Queues / Workflows）で実行する

| 項目 | 値 |
|---|---|
| 状態 | 採択 |
| 日付 | 2026-08-22 |

## 文脈

Cloudflare Workers には1リクエストあたりの実行時間・CPU時間の制約がある。
一方、本システムには次のような長時間処理がある。

| 処理 | 想定所要 |
|---|---|
| Claim 分解（1特許） | 数十秒 |
| AI模擬審査（先行文献10件との比較） | 数分 |
| 自律エージェント連鎖（M21、15段階） | 数十分 |
| 帳票生成（50ページPDF） | 数十秒 |
| 特許データの日次取り込み | 数時間 |

これらを同期APIで実装すると、実行時間制約に抵触し、UX上も長時間の待機を強いる。

## 決定

**60秒を超える可能性のある処理はすべて非同期とする。**

| 処理種別 | 実行基盤 |
|---|---|
| 単発のAI処理、帳票生成、取り込み | **Cloudflare Queues** + Consumer Worker |
| 多段の依存があるエージェント連鎖（M21） | **Cloudflare Workflows** |

API 契約:

```text
POST /v1/ai/runs        → 202 Accepted { run_id, status: "queued" }
GET  /v1/ai/runs/{id}   → { status, progress, result?, citations? }
GET  /v1/ai/runs/{id}/events  → SSE（進捗のストリーム）
```

## 理由

- 実行時間制約を構造的に回避できる
- 失敗した step のみを再試行でき、全体をやり直さずに済む
- Workflows は状態を永続化するため、中断・再開・進捗追跡が可能（FR-M21-002/003 を満たす）
- 利用者は待機画面に拘束されず、他の作業を進められる

## 結果

**良い点**: 制約の回避、再試行の粒度が細かい、進捗が可視化できる
**悪い点**:

- 画面実装が複雑になる（ポーリング／SSE、進捗表示、失敗時の再実行UI）
- ジョブの滞留・DLQ の運用監視が必要になる
- 「実行したのに結果が見えない」体験を避けるため、通知設計が必須

**必須の付随設計**

1. すべてのジョブに `status`（queued / running / succeeded / failed / cancelled）を持たせる
2. 進捗率または現在ステップ名を返す
3. 失敗時は原因と再実行手段を画面に出す
4. 滞留数・DLQ 件数を監視しアラートする

## 代替案

| 案 | 不採用の理由 |
|---|---|
| 同期APIで実装 | 実行時間制約に抵触。UXも不適 |
| 外部のジョブ基盤を併設 | 運用対象が増える。Cloudflare 一本化の方針に反する |
| ポーリングのみ（SSE なし） | 長時間ジョブで無駄な問い合わせが増える。SSE を併用する |

## 再評価条件

- Workers の実行時間制約が大きく緩和された場合（短時間処理の一部を同期化しうる）
- ジョブ滞留が常態化し、キュー構成の見直しが必要になった場合
