# ADR-0003 日本語検索を pg_trgm + pgvector のハイブリッドで実現する

| 項目 | 値 |
|---|---|
| 状態 | 採択（再評価条件あり） |
| 日付 | 2026-08-22 |
| 重要度 | **高**。本システムの主機能に直結する |

## 文脈

本システムの中核は横断検索である。対象は日本語の特許明細書・請求項・論文・NETIS・技術台帳。

PostgreSQL の標準全文検索（`tsvector`）は空白区切りを前提としており、
**日本語を語に分割できない**。日本語対応の一般的な解は PGroonga や pg_bigm だが、
**Neon ではこれらの拡張が利用できない**（利用可能拡張に含まれない）。

一方で pgvector（ベクトル検索）と pg_trgm（トライグラム）は利用できる。

## 決定

以下のハイブリッド検索とする。

| 経路 | 手段 | 得意 |
|---|---|---|
| **字句検索** | `pg_trgm` のトライグラム類似度 + 正規化済みキーワードの完全／前方一致 | 特許番号、企業名、固有名詞、型番 |
| **意味検索** | `pgvector`（HNSW インデックス、コサイン距離） | 言い換え、概念的な近さ、自然文の質問 |
| **融合** | RRF（Reciprocal Rank Fusion） | 双方の順位を統合し単一の順位を返す |

加えて、取り込み時に **AI による正規化キーワード・技術要素の抽出** を行い、
`search_keywords` として構造化して保存する。これが字句検索の精度を補う。

## 理由

- Neon の制約下で、追加の運用対象を増やさずに実装できる
- 業務データと同一DB・同一トランザクション・同一権限で扱えるため、C3/C4 の制御が一箇所で済む
- 特許検索では「番号・企業名の完全一致」と「概念的な近さ」の両方が必要であり、ハイブリッドが要件に合う
- RRF はスコアのスケールを揃える必要がなく、実装が単純で挙動が安定する

## 結果

**良い点**

- 運用対象が増えない。権限制御が単純
- 自然文検索が最初から機能する（意味検索が主役になれる）

**悪い点 / 受け入れるリスク**

- ⚠️ **トライグラムは日本語の語境界を認識しない**。短い語や助詞を含む検索で雑音が増える
- ⚠️ トライグラム索引はデータ量に対して大きくなりやすく、更新コストがかかる
- ⚠️ 埋め込みモデルの品質に検索品質が強く依存する
- 大規模データでの再現率・適合率は実測しないと分からない

**必須の緩和策**

1. Phase 1 で **検索品質の実測** を行う（代表50クエリの正解セットを作り、再現率・適合率を測る）
2. 取り込み時のキーワード抽出・分類付与を丁寧に行う（字句検索の弱さを構造で補う）
3. 検索対象フィールドを分け、重み付けを調整可能にする（タイトル > 請求項 > 明細本文）
4. 利用者が検索式を編集できるようにし、AI任せにしない

## 代替案

| 案 | 内容 | 不採用の理由 |
|---|---|---|
| PGroonga / pg_bigm | 日本語全文検索の定番 | Neon で利用できない |
| 外部検索エンジン（Elasticsearch / OpenSearch 等） | 日本語解析器が使える | 運用対象が増える。権限・機密区分の二重管理が発生する。Phase 3 で再評価 |
| Cloudflare の全文検索サービス | 基盤内で完結 | 日本語解析の要件を満たすか未確認。⚠️ 要調査 |
| クライアント側での形態素解析 + 転置索引の自前実装 | 制御可能 | 実装・運用コストが見合わない |

## 再評価条件

以下のいずれかに該当した場合、外部検索エンジンの併設を再検討する。

1. Phase 1 の実測で、代表クエリの再現率が業務上許容できない水準だった
2. トライグラム索引のサイズ・更新コストが Neon の制約に抵触した
3. 利用者から「探しているものが出てこない」との報告が継続的に発生した
4. 特許データ量が想定の数倍を超えた

**再評価の期限**: Phase 1 完了時に必ず一度評価し、結果を本 ADR に追記する。
