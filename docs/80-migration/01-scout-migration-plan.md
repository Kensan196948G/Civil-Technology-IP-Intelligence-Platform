# 📦 Civil-Research-Patent-Scout 移管計画

## 1. 方針

旧システム `Civil-Research-Patent-Scout` の**全資産を評価対象**とし、有効なものを CTIIP へ移管する。
機能だけでなく、データ・設計書・API・DB定義・テスト・CI/CD・Issue・Git履歴・運用資料を含む。

移管完了後にアーカイブし、並行稼働期間を経て廃止する。

## 2. 対応表

| 旧（Scout） | 新（CTIIP） | 扱い |
|---|---|---|
| Patent Search | M04 Patent Intelligence | 機能移管。UI は新規 |
| Research Search | M08 Research & Paper Intelligence | 機能移管 |
| AI Summary | `packages/ai` + 各モジュール | 再実装（Provenance 対応が必要） |
| Technology Search | M03 Technology Intelligence | 機能移管 |
| Patent Classification | M04 + M24 | 再実装（正規化を強化） |
| Civil Classification | M12 Civil Engineering Intelligence | 移管 + 拡張 |
| Database | 新統合DB（Neon） | **データ移行**（§4） |
| API | `apps/api` | 再設計（REST v1） |
| UI | `apps/web` | 参考としつつ新規実装 |
| Documents | `docs/` | 有効なものを取り込み |
| Tests | `60-quality` 体系 | 有効なケースを移植 |
| CI/CD | `.github/workflows/` | 新規作成（旧設定を参考） |
| Issue | GitHub Issues | 有効なものを新Repoへ転記 |
| Git 履歴 | — | ⚠️ **要決定** — 参照用にアーカイブとして保持 |

## 3. 評価の観点

各資産について次を判定する。

| 判定 | 意味 |
|---|---|
| **移管** | そのまま、または軽微な調整で新システムへ移す |
| **再実装** | 考え方は活かすが、新しい設計要件（Provenance、権限、非同期）に合わせて作り直す |
| **参考** | 実装は移さないが、設計判断の参考にする |
| **破棄** | 使わない。理由を記録する |

**MUST**: 「破棄」と判定したものは理由を記録する。後から「なぜ捨てたか」を追えるようにする。

## 4. データ移行

### 4.1 手順

```text
① 旧DBのスキーマとデータ量を調査
② 新スキーマへのマッピング表を作成（列単位）
③ 変換スクリプトを作成
④ 検証環境で試行 → 件数・整合性を検証
⑤ 品質チェック（欠損・重複・文字化け）
⑥ 🔒 承認のうえ本番へ移行
⑦ 移行後の検証（件数突合、サンプル比較）
⑧ 並行稼働期間の設定
```

### 4.2 移行時の必須処理

| # | 処理 | 理由 |
|---|---|---|
| 1 | `source` / `source_url` / `retrieved_at` を補完する | Provenance の要件。不明な場合は「移行時不明」として明示的に記録 |
| 2 | 機密区分（`classification`）を付与する | 旧システムに無い概念の可能性。既定値の方針を決める |
| 3 | 文字コード・正規化を統一する（NFKC） | 検索の前提 |
| 4 | 名寄せ状態を引き継ぐ、または再実行する | 集計の正しさ |
| 5 | 埋め込みは**新規生成**する | モデルが異なるため流用しない |
| 6 | 旧AI出力は根拠がなければ移行しない | 根拠なしの出力を新システムへ持ち込まない |

⚠️ **重要**: 旧システムの AI 生成物（要約・分類など）に根拠が伴わない場合、
そのまま移行すると Provenance 原則が最初から破られる。
**根拠のない旧AI出力は移行せず、必要なら新システムで再生成する。**

### 4.3 検証項目

| # | 項目 | 方法 |
|---|---|---|
| 1 | 件数の一致 | テーブル別に突合 |
| 2 | 主要データのサンプル比較 | 無作為 100 件を目視 |
| 3 | 文字化けの有無 | 特許特有の記号を含むレコードを抽出 |
| 4 | 参照整合性 | 外部キーの孤立を検出 |
| 5 | 機密区分の妥当性 | 分類別件数を確認 |
| 6 | 検索の動作 | 移行データで検索品質を測定 |

## 5. 並行稼働と廃止

```text
Phase 1 完了時点
   ↓ 新システムで基本機能が稼働
並行稼働期間（⚠️ 期間は要決定。暫定 3か月）
   ├ 新システムを正本とする
   ├ 旧システムは参照専用（書き込み停止）
   └ 差異の報告を受け付ける
   ↓ 問題がないことを確認
旧システムをアーカイブ（読み取り専用で保存）
   ↓ ⚠️ 保存期間は要決定
廃止
```

**MUST**:
- 並行稼働中は**書き込みを新システムのみに限定**する。両方に書くと不整合が生じる
- 廃止の判断は 🔒 承認事項とする

## 7. リスク

| リスク | 対策 |
|---|---|
| 旧データの品質が低く、移行後の検索品質が落ちる | 移行前に品質チェック。低品質データは移行対象から外すか、フラグを立てる |
| 根拠のない旧AI出力の混入 | 移行しない方針を明記（§4.2） |
| 機密区分の誤付与 | 既定を厳しい側（C2 以上）に倒し、公開情報のみ C1 とする |
| 並行稼働中の二重書き込み | 旧システムを参照専用にする |
| 移行の長期化 | 移行対象を絞る。全件移行に固執しない |
| 旧システムの知見喪失 | 廃止前に運用資料・設計判断を `docs/` へ取り込む |
