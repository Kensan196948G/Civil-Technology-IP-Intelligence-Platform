# 🚨 障害・インシデント対応

## 1. 重大度

| 区分 | 定義 | 例 | 初動 |
|---|---|---|---|
| **P1** | 情報保護または全面停止に関わる | 認証の不全、機密の露出、データ破損、全面停止 | 直ちに。システムオーナーへ即報 |
| **P2** | 主要機能が使えない | 検索不能、AI処理が全件失敗、ジョブ全停止 | 当日中 |
| **P3** | 一部機能の不具合・性能劣化 | 特定画面のエラー、バッチ遅延 | 翌営業日 |
| **P4** | 軽微 | 表示崩れ、文言の誤り | 通常の改修 |

## 2. 初動（共通）

```text
① 検知（アラート・利用者報告・監視）
② 重大度を判定
③ 記録を開始（時刻・事象・影響範囲・対応者）
④ 影響の拡大を止める
     - 情報漏えいの疑い → 該当機能・公開を停止
     - データ破損の疑い → 書き込みを止める
⑤ 関係者へ連絡
⑥ 原因調査（相関IDを軸に）
⑦ 復旧
⑧ 検証
⑨ 報告
⑩ 再発防止
```

**MUST**: ④を⑥より先に行う。原因究明のために被害を拡大させない。

## 3. 種別ごとの対応

### 3.1 認証・認可の不全（P1）

```text
症状: 未認証でアクセスできる／権限のない情報が見える
① 直ちに公開を止める（Custom Domain を外す、または Access ポリシーで全拒否）
② 監査ログで、どの利用者が何にアクセスしたかを特定
③ 原因を特定（JWT 検証の不備、権限条件の欠落、ポリシー設定）
④ 修正 → 緊急デプロイ手順（テストは省略しない）
⑤ 影響を受けた情報の範囲を特定し、関係者へ報告
⑥ 未公開発明が含まれる場合、権利化への影響を知財部門と評価する
```

**MUST**: 未公開の発明情報が露出した可能性がある場合、
**新規性喪失の可能性**として知財部門へ直ちに報告する。技術的な復旧だけで終わらせない。

### 3.2 情報漏えいの疑い（P1）

```text
① アクセス経路を遮断
② 監査ログで痕跡を保全（改変しない）
③ 漏えい範囲・対象データの機密区分を特定
④ システムオーナー → 経営へ報告
⑤ 必要に応じて外部専門家・法務へ相談
⑥ 再発防止（権限設計、監査の強化）
```

### 3.3 データ破損（P1）

```text
① 書き込みを停止
② 破損範囲を特定
③ [復旧手順](03-backup-and-restore.md) に従う
④ 復旧後のデータ検証
⑤ 原因（バグ・マイグレーション・操作ミス）を特定し、再発防止
```

### 3.4 全面停止（P1）

```text
① 障害箇所の切り分け（Cloudflare / Neon / 外部API / アプリ）
② 基盤側の障害なら状況を確認し、復旧を待つ間の告知を行う
③ アプリ起因ならロールバック
④ 復旧確認
```

### 3.5 AIプロバイダ障害（P2）

```text
① AI機能の縮退表示に切り替わっていることを確認
② 検索・台帳参照が継続できていることを確認
③ 滞留したジョブを再実行キューへ
④ 復旧後、再実行
```

**MUST**: AI が使えないことを理由に、検索・参照まで止めない。

### 3.6 ジョブ滞留・DLQ（P2〜P3）

```text
① DLQ の内容を確認し、原因を分類
② 一時的な失敗 → 再投入
③ 恒久的な失敗（データ不正・仕様変更）→ dq_issues に起票し、取り込み処理を修正
④ 滞留が続く場合、優先度の低いジョブを停止して主要機能を守る
```

### 3.7 外部データ源の仕様変更（P3）

```text
症状: 取り込み件数の急変、スキーマ検証エラーの多発
① 取り込みを一時停止（誤ったデータの流入を止める）
② 取得元の変更内容を確認
③ 取り込みアダプタを修正
④ 影響を受けた期間のデータを再取り込み
```

## 4. 記録すべき事項

| 項目 | 内容 |
|---|---|
| 検知 | 日時、検知方法、第一報者 |
| 事象 | 症状、影響範囲、影響を受けた利用者・データ |
| 対応 | 実施した操作を時系列で |
| 原因 | 直接原因と根本原因 |
| 復旧 | 完了日時、確認方法 |
| 再発防止 | 対策、実施期限、担当 |
| 残課題 | — |

**MUST**: 機密データの本文を記録に含めない。識別子と件数で記述する。

## 5. エスカレーション

| 状況 | エスカレーション先 |
|---|---|
| P1 全般 | システムオーナー → 経営 |
| 未公開発明の露出 | 知財部門 → システムオーナー → 経営 |
| 個人情報の関与 | 管理本部（法務） |
| 外部への影響 | 経営（対外説明の要否を判断） |
| 復旧不能 | 経営（事業影響の判断） |

## 6. 再発防止の原則

| # | 原則 |
|---|---|
| 1 | 同一原因の障害を3回起こさない。2回目で設計を見直す |
| 2 | 「注意する」で終わらせない。仕組みで防ぐ |
| 3 | 再発防止策には期限と担当を付ける |
| 4 | テストを追加し、CI で検出できるようにする |
| 5 | 手順の不備は手順書を更新する |
